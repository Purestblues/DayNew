Windows 优先 · 数据完全自建 · 坚果云 WebDAV 同步 · 讨论稿，未开工
01 · 定位

这不是日历软件，是任务软件

需求集中在截止日期、长期项目、习惯重复、缴费提醒——没有一项是「几点到几点开会」。两者的内核不同：日历的对象是时间块（要与人协作、要看到别人空闲），任务的对象是待办的事（可能没有时刻，只有「该做了」和「什么时候必须做完」）。

按日历的思路做，用户会被迫填开始时间和结束时间，而这正是 Outlook 让人烦的根源。所以本项目里，日历月视图是可选视图，不是主干。

约束含义它排除了什么
一台电脑 + 一台安卓必须有同步，无法回避纯单机方案
数据完全自建不依赖任何厂商云Google / Outlook 账号集成
简洁轻快无动效、无材质、无重框架跨平台 UI 框架、花式过渡
看见就拖，不填表没有「新建日程」表单属性面板、必填字段、弹窗流程

03 · 数据模型

一条任务只有这些字段

{
  "id":   "01J8…",              // UUID，永不变
  "t":    "交电费",              // title
  "n":    "",                   // note，折叠
  "tags": ["生活"],
  "due":  "2026-11-20",          // 可空 → 空即「某天」档
  "ord":  1024,                 // 档位内排序，稀疏值便于插入
  "rep":  { "f": "monthly", "d": 20 },   // 可空
  "rm":   "09:00",              // HH:mm，空 = 不提醒
  "done": false, "doneAt": null,
  "del":  false,                // 墓碑，给同步用
  "hlc":  "0012-8f3a-win"       // 混合逻辑时钟，UI 永不显示
}

关键：档位不是字段，是算出来的。「今天」= due 等于今天，「某天」= due 为空，「逾期」= 有日期且早于今天且未完成。所以把卡片从一个档拖到另一个档，本质只是改 due 一个值——这才是一步就能完成、不需要打开任何表单的原因。

05 · 同步

每台设备只写自己的文件

WebDAV 本质是 HTTP 文件读写：没有锁、没有事务、没有「追加」。所以不能把整个库存成一个文件让两端轮流上传——后到的会把先到的整个覆盖，丢数据是必然的。

改用一条谁都不会违反的规则：每台设备只写自己那个文件，永远不碰别人的。这样冲突在结构上就不可能发生。

坚果云 / 日历库 /
    device-win.json.gz       ← 只有 Windows 写
    device-android.json.gz   ← 只有安卓写
列目录 1 次→ 下载别人更新的 0~1 次→ 本地字段级合并→ 上传自己的 0~1 次
项说明
请求预算一次同步 2~4 个请求。一天 20 次 ≈ 60 个请求，免费账号限额是 30 分钟 600 个，余量极大
文件数量恒等于设备数（2 个），不会随年月增长。坚果云「单层 500 文件」的限制碰不到
合并粒度字段级。同一个字段两边都改，两个值都留着标成待处理，点一下选，最坏是多一条，不是少一条
文件内容全量（不是增量）。十年数据压 gz 后约几百 KB，可接受
删除墓碑标记，不真删，否则另一台设备会把它「复活」

P3 MCP 设计（参照 Taix / 时见）

  • 主进程内嵌服务端：日新没有独立后台服务，由 WPF 主进程直接兼任服务端，开启仅监听 127.0.0.1 的 Streamable HTTP /mcp 端点（暂定端口 37092，避开 Taix 的 37091）；默认关闭，使用本地生成的 Bearer Token 鉴权（常数时间比对，未开启返回 403，Token 错误返回 401），并通过 SERVER_INSTRUCTIONS 向 agent 声明红线。
  • 单写者模型（Dispatcher + 现有入口）：所有工具调用切回 UI 线程（Dispatcher）执行，写操作经 DayStore 与 MainViewModel 现有入口（SaveEditor 校验、FindFreeStart 防重叠、ToggleDone → CompletionLog.Append），再由现有防抖落盘写文件。MCP 与界面操作同一份内存对象，彻底避免第二个进程写 data.json。
  • 极薄 STDIO 桥接回退：不支持 HTTP 的客户端可回退至 DayNew.exe --mcp；在 Program.cs 的 VelopackApp.Build().Run() 之后、单实例 Mutex 与 WPF 启动之前分流，不加载 data.json、不抢 Mutex，仅转发 stdin/stdout 的 JSON-RPC 到本机 /mcp（默认从本地配置读 Token，支持 --url / --token 或环境变量覆盖）。
  • 使用前置条件：App 必须处于运行状态，MCP 才能提供服务；App 未启动时，桥接需直接返回明确错误提示（「请先启动日新」），禁止绕过主程序自行读写 data.json。托盘常驻与开机静默自启已实现，关闭窗口默认缩到托盘，所以实际上 App 一直在线；只有从托盘「退出」后 MCP 才不可用。
  • 能力边界与红线：日程 / 标签 / 目标的新增与修改可直接执行；删除类操作开放权限，但执行前必须走双层即时确认：① 协议层将删除拆为独立工具并标注 destructiveHint: true，在 SERVER_INSTRUCTIONS 与工具描述中要求 agent 提前说明待删对象及影响范围并征得同意；② App 端硬拦截——服务端运行在本地 WPF 进程内，删除落盘前由日新弹出本地即时确认（明确展示待删明细，提供「允许删除 / 拒绝」并设超时如 60 秒），用户当场同意才执行，拒绝或超时则返回错误，防止 agent 跳过询问或客户端自动放行。其余红线不变：完成状态仅通过 ToggleDone 切换，completions.ndjson 只追加、不改写或删除历史；导出可开放为只读；导入覆盖、回滚、WebDAV 配置与密码、MCP Token 一律对 MCP 屏蔽。
  • 工具清单草案：get_overview（按档位分组的日程）、list_schedules（支持按日期区间 / 标签 / 目标 / 完成状态过滤与分页）、get_schedule、create_schedule、update_schedule、delete_schedule、set_done、list_tags / save_tag / delete_tag、list_goals / save_goal / delete_goal、get_completions（只读）；其中所有 delete_* 工具均标注 destructiveHint: true 并强制走 App 端即时确认闸口。
  • 设置页接入体验：设置页新增「AI 与 MCP」区，提供开关、Bearer Token 查看与重新生成、端点展示，以及「复制安装提示词」按钮（让用户发给 agent 按「HTTP 优先、STDIO 回退」自动配置并自检）。

07 · 风险与待验证

写在纸上不代表跑得通

必须实测的

  • 坚果云 PUT 一个几百 KB 的 gz 文件是否稳定，是否有单文件大小限制
  • 坚果云是否支持 If-Match / ETag（能省请求、能做乐观锁）
  • 是否支持 MOVE（原子替换文件，避免上传中断留半个文件）
  • 应用专属密码的认证方式与 WebDAV 根路径

已知的坑

  • 坚果云频繁改文件会返回 503，同步必须退避重试，不能死循环
  • PROPFIND 列目录在大目录会超时 → 目录必须保持扁平
  • 两台设备时钟不准会导致「谁更新」判断错 → 用 HLC 而不是系统时间
  • 重复任务推进日期要按日历算，不能用 +86400 秒（夏令时/闰月会歪）
