日程管理软件 · 方案 v0.1

Windows 优先 · 数据完全自建 · 坚果云 WebDAV 同步 · 讨论稿，未开工
01 · 定位

这不是日历软件，是任务软件

需求集中在截止日期、长期项目、习惯重复、缴费提醒——没有一项是「几点到几点开会」。两者的内核不同：日历的对象是时间块（要与人协作、要看到别人空闲），任务的对象是待办的事（可能没有时刻，只有「该做了」和「什么时候必须做完」）。

按日历的思路做，用户会被迫填开始时间和结束时间，而这正是 Outlook 让人烦的根源。所以本项目里，日历月视图是可选视图，不是主干。

约束含义它排除了什么
一台电脑 + 一台安卓必须有同步，无法回避纯单机方案
数据完全自建不依赖任何厂商云Google / Outlook 账号集成
简洁轻快无动效、无材质、无重框架跨平台 UI 框架、花式过渡
看见就拖，不填表没有「新建日程」表单属性面板、必填字段、弹窗流程

03 · 数据模型

一条任务只有这些字段

{
  "id":   "01J8…",              // UUID，永不变
  "t":    "交电费",              // title
  "n":    "",                   // note，折叠
  "tags": ["生活"],
  "due":  "2026-11-20",          // 可空 → 空即「某天」档
  "ord":  1024,                 // 档位内排序，稀疏值便于插入
  "rep":  { "f": "monthly", "d": 20 },   // 可空
  "rm":   "09:00",              // HH:mm，空 = 不提醒
  "done": false, "doneAt": null,
  "del":  false,                // 墓碑，给同步用
  "hlc":  "0012-8f3a-win"       // 混合逻辑时钟，UI 永不显示
}

关键：档位不是字段，是算出来的。「今天」= due 等于今天，「某天」= due 为空，「逾期」= 有日期且早于今天且未完成。所以把卡片从一个档拖到另一个档，本质只是改 due 一个值——这才是一步就能完成、不需要打开任何表单的原因。

05 · 同步

每台设备只写自己的文件

WebDAV 本质是 HTTP 文件读写：没有锁、没有事务、没有「追加」。所以不能把整个库存成一个文件让两端轮流上传——后到的会把先到的整个覆盖，丢数据是必然的。

改用一条谁都不会违反的规则：每台设备只写自己那个文件，永远不碰别人的。这样冲突在结构上就不可能发生。

坚果云 / 日历库 /
    device-win.json.gz       ← 只有 Windows 写
    device-android.json.gz   ← 只有安卓写
列目录 1 次→ 下载别人更新的 0~1 次→ 本地字段级合并→ 上传自己的 0~1 次
项说明
请求预算一次同步 2~4 个请求。一天 20 次 ≈ 60 个请求，免费账号限额是 30 分钟 600 个，余量极大
文件数量恒等于设备数（2 个），不会随年月增长。坚果云「单层 500 文件」的限制碰不到
合并粒度字段级。同一个字段两边都改，两个值都留着标成待处理，点一下选，最坏是多一条，不是少一条
文件内容全量（不是增量）。十年数据压 gz 后约几百 KB，可接受
删除墓碑标记，不真删，否则另一台设备会把它「复活」

07 · 风险与待验证

写在纸上不代表跑得通

必须实测的

  • 坚果云 PUT 一个几百 KB 的 gz 文件是否稳定，是否有单文件大小限制
  • 坚果云是否支持 If-Match / ETag（能省请求、能做乐观锁）
  • 是否支持 MOVE（原子替换文件，避免上传中断留半个文件）
  • 应用专属密码的认证方式与 WebDAV 根路径

已知的坑

  • 坚果云频繁改文件会返回 503，同步必须退避重试，不能死循环
  • PROPFIND 列目录在大目录会超时 → 目录必须保持扁平
  • 两台设备时钟不准会导致「谁更新」判断错 → 用 HLC 而不是系统时间
  • 重复任务推进日期要按日历算，不能用 +86400 秒（夏令时/闰月会歪）
